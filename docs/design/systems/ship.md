# 船体与分区

设施是一艘船。地形本身是可读的，`python3 tools/show_terrain.py` 会把平面图、放置物件和所有区域一起打出来，并报出每个区域占甲板的百分比——**"这些区是不是我想要的大小"是画分区图唯一要回答的问题**，所以那一栏就在图例里。

| | |
|---|---|
| 地图 | **192×248 格**（船体加长过一次，纵向从 192 加到 248） |
| 可玩区（playable area） | x 10..182、y 8..228 |
| 可走甲板 | 20,006 格 |
| 船长 | 约 220 格 → 员工（速度 2.25）**从头走到尾 98 秒** |
| 地形集 | `KorhalPlatformEx2` |

> **可玩区不是镜头范围，差一圈。**按可玩区画出来的平面图带着一圈**镜头永远够不到的边**，船看起来比实际能玩的更长。
>
> **`MapInfo` 里只有可玩区那一个矩形**（偏移 64 起，四个 8 位定点数）。镜头范围在编辑器里单独设，而且它的数值**在地图的任何文件里都搜不到**——按整数、按定点、按浮点都搜过。所以 `show_terrain.py` 默认画可玩区并且如实标出来，要看真的就 `--bounds L B R T`。
>
> 上一版（192×192）量过一次两者的差别：镜头只切掉 2% 的甲板，六个区的占比挪动都不到半个百分点。**这套分区对按哪个矩形量不敏感。**

## 六个区

**分区和部门解耦。**任何部门都可以坐在任何一个区里。唯一的倾向是**中央本部偏好 `zone_amidships`**——它的技能是全船性的，坐在中间最好使——而且这只是倾向，不是约束。

所以区的名字用航海方位，不用部门名。

六个矩形按清理后的船体（可走范围 x 18..173、y 26..215）画好了：

| 区域 | 范围 | 甲板占比 | 意图 |
|---|---|---|---|
| `zone_amidships` | x 64..127，y 96..161 | **20.1%** | 稍大 |
| `zone_aft_port` | x 18..95，y 26..95 | 18.1% | 正常 |
| `zone_aft_starboard` | x 96..173，y 26..95 | 18.1% | 正常 |
| `zone_bow` | x 18..173，y 162..215 | 17.3% | 正常 |
| `zone_engine_port` | x 18..63，y 96..161 | **13.2%** | 偏小 |
| `zone_engine_starboard` | x 128..173，y 96..161 | **13.2%** | 偏小 |

**六块盖住全部 20,584 格甲板，一格不漏，左右完全相等。**最大/最小 1.52×。

> **外缘收在可走范围的包围盒上，不再画到可玩区边上。**先前画到 10 / 8 / 182 / 228 是个错误：那几条边**在镜头范围之外，编辑器里根本滚不过去，也就点不到**——而区域是靠点它的边框来选中的。

**它们是矩形，而且故意是矩形。**边界最终要由舱壁来落实；这六个矩形是**给舱壁用的标线**，在编辑器里拖一下就能改，改完 `show_terrain.py` 立刻重新报数。

> 加长那次的教训：**编辑器把所有区域连同地形一起 +24 平移了**，所以左右和相对位置一格没错；但**新加出来的艏部整段落在 `zone_bow` 外面**（六个区加起来只剩 88%），而且新船长把内部分界的最优位置也挪了。船体一改形状，**平移是白送的，重新拟合不是**。

> **这六个区不是防御地点。**`Fort_BuildRegistry` 只收名字以 `room_` 或 `corridor_` 开头的区域，所以 `zone_` 前缀天然不会污染 `gvg_loc*` 那张表。同理 `resthall1` 也不是——它是休息室，不是可升级的房间。

## 船体自己的形状

**左右镜像，前后不对称。**六个区在这种形状上只有一种自然分法：**两个骑在中轴上的区，加两对镜像**。上表正是——`bow` 和 `amidships` 在中轴，两个 `engine_*` 一对，两个 `aft_*` 一对。这不是凑出来的，是船形逼出来的。

一个对中央本部有用的副产品：**`amidships` 同时和其余五个区都接壤**（前接 `bow`、左右接两个 `engine_*`、后接两个 `aft_*`）。支援型部门坐这儿，去任何地方都不用穿过第三个区。

## 唯一一条硬性地形要求：把中后舱壁往前推

**船体自己在 y≈78 有一处收窄**（宽度从 112 掉到 96 再弹回 116），**而尺寸需要的分界线在 y=90**。差 12 格，而这 12 格把结果翻过来：

| 中后分界线 | bow | amidships | engine ×2 | aft ×2 |
|---|---|---|---|---|
| **y=90**（现在这套） | 17.3% | 19.9% | **13.4 / 13.1** | **18.1 / 18.1** |
| y=84 | 17.3% | 21.7% | 14.4 / 14.0 | 16.3 / 16.3 |
| **y=78**（船体的收窄处） | 17.3% | 23.4% | **15.0 / 14.7** | **14.8 / 14.8** |

**顺着那处收窄切，引擎侧和后两区会拉平到 15% 上下**——"引擎侧偏小"就没有了，中央也会胀到 23.4%。

所以中后舱壁要落在 **y≈90**，而不是船体现在收窄的地方；或者让后两区沿侧舷越过那处收窄往前伸。

> 加长之前这个差距是 18 格，现在是 12 格。**加长把它缩小了，但没有消掉。**

## 先给中央一个轮廓

整个中段的面积里，**唯一的内部结构就是那两个引擎盒**（各带一个 6×6 的空腔，现在在 x 58-63 / x 128-133、y 124-129）。

它们位置极好：正压在 `amidships` 和两个 `engine_*` 的分界外侧，**引擎侧那个区天生就有锚点**，所以"引擎侧偏小"这件事地形已经在帮忙了。

而 **`amidships`——最大、也最需要一眼认得出来的那个区——一格特征都没有。**中央本部要坐在这儿，五个方向都通向它，它却是全船最没有形状的地方。

**只改一处的话，先给中央一个轮廓。**它一成形，`amidships/engine_*` 那两条边界就同时有了，五条里去掉两条。

## 一个必须记住的约束：`Sector_OwnerNear` 穿墙

**归属是"最近的核心"，纯欧氏距离，不认墙**（`09_sector.galaxy`）。`Fort_OwnerOf`、`Cont_OwnerOf` 的兜底、`50_waves` 的哨位归属都走它。

所以砌完舱壁之后，**核心的位置必须让 Voronoi 的分界线落在舱壁上**。落不上，就会出现一间物理上在 A 区、却答应 B 部门的房间——而且**全场没有任何提示**：那个部门升级不了自己的房间，考验刷在别人家，防御任务算错数。

还有一条更省事的路：**让地点的归属跟着区域走，而不是跟着距离走**——区域名本来就是一条通道（`Fort_LocByName` 已经在用），让 `room_*` / `corridor_*` 落在哪个 `zone_*` 里就归谁。这不是新开通道。等舱壁定型再决定。

## 区域名不能重复，构建会拦

**编辑器改地图尺寸的时候，把 `resthall1` 和 `corridor_a` 各复制了一份**——同名、同 id、同矩形，两条。构建当时照单全收，什么都没说。

这不是排版问题：**脚本问编辑器要东西，全都是按名字要的**（`ObjectsGen_Region`、`Fort_LocByName`、fort/debris 编组）。同名两条＝一个问题两个答案，而且没法说清是哪个——`Fort_BuildRegistry` 会把同一条走廊登记成两个地点，于是在其中一个上买的防御升级，另一个仍然是 0 级；考验抽到那条走廊的概率翻倍；所有对地点的计数都少算或多算一个。**全场一个字都不会提。**

`check_unique` 现在会当场拦下重名的区域和编组（第十一道构建检查）。

**id 也一样，而且那一半是编辑器的事，不是我们的。**`Region 001` 和 `resthall1` 一度都是 id 1——脚本这边毫无影响（我们按名字查），构建照常打印两条，但**编辑器按 id 编号，撞了 id 的那一条在编辑器里就选不中了**。这个症状从脚本这边永远看不出来，所以 `check_unique` 连 id 一起查。
