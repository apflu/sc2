# P0 灰盒原型：范围与验证目标

## 唯一要验证的命题

> 玩家只有一双手，而**挖、打、修**三件事同时在抢他。

这是 `gameplay-baseline.md §9` 的核心张力，整个设计的地基。如果玩起来发现三件事其实不冲突——挖完就没事干，或者打架时根本不用管别的——那部门、协作、两层扇区全都建在沙子上。

P0 只做能验证这一条的最小集，其余一律推后。

## 已实现

| 内容 | 模块 |
|------|------|
| 玩家角色：交接、选中、死亡后定点重生 | `15_hero.galaxy` |
| 残骸清理（玩家亲手 / 工人自动） | `25_clearing.galaxy` |
| 清理产出 → 内层矿脉堆 | `25_clearing.galaxy` |
| 矿脉堆 → 物资（按矿工数量自动转化） | `40_economy.galaxy` |
| 设备周期产电、致命伤失能、可修复 | `20_devices.galaxy` |
| 工人自主派工（修优先于挖） | `30_workers.galaxy` |
| 定时虫波 | `50_waves.galaxy` |
| 启动自检与灰盒读数 | `10_registry.galaxy` / `40_economy.galaxy` |

**失能不是独立状态位**：设备血量高于阈值就在线，低于就停产；致命伤被拦截并把血量钳到 1 而不是让它死。于是修复就是原生 SCV 维修能力把血加回来，设备自己恢复在线。血条直接显示失能状态，不需要专门的修复机制，也没有一个会和单位本身失同步的状态位。

**清理建模为伤害而非自定义进度条**：残骸是高血量可破坏物，玩家和工人都靠攻击它来清理。这样血条直接充当进度反馈，而"玩家远快于工人"变成纯粹的武器数值问题，落在数据层可以随便调，而不是写死在脚本里的两个速率常数。

**玩家角色刻意不是工人**：`Lob_Hero_Agent` 没有采集、没有建造。抢它的只有要验证的那三件事，别的一概砍掉——这样"玩家很忙"就只剩一种解释。死亡只花时间：原地复活、不掉资源、角色不留惩罚，代价是走回来的路程加上这段时间里塌掉的东西（基线 §1）。

## 明确砍出 P0 的

**作业标记 + 队列 UI。**工人目前自动指派到最近的残骸。

理由：要验证的命题是"玩家自己的时间不够分配"，而玩家的取舍是关于**他本人在干什么**，不是关于微观调度工人。加一套下达指令的 UI 会给玩家增加第四件事，但对验证这条命题没有贡献，反而会让"手忙"的来源变得不可归因——测出来忙，分不清是设计成立还是 UI 笨重。

推到 P0.5。届时它需要一个英雄的目标性技能（数据层工作）。

同样推后的还有：防御工事、部门、理智、多人、多扇区。

**电力目前只是个累加的数字**，还没有消耗端（照明、工事运行）。它先存在，是为了让设备失能有可见后果。

## 数值起点

全是拍脑袋的占位，测的时候直接改：

- `Lob_Hero_Agent`：250 血、护甲 1、每秒回 1、移速 3.0
- `Lob_Hero_Rifle`：20 伤害 / 1.0 秒 / 射程 5 = 20 DPS
- `Lob_Debris_Normal` `LifeMax` = 600，`LifeArmor` = 0
- 每块残骸产出 25 点矿脉堆额度（`c_oreCreditPerDebris`）
- 每个矿工每 2 秒转化 5 点（`c_minePerMinerPerTick`）
- 每个在线设备每 3 秒产 3 点电（`c_powerPerDevicePerTick`），血量低于 50% 停产
- 每 45 秒一波虫子，每个入口 `3 + 波次数` 只跳虫（`c_waveInterval` / `c_waveBaseSize`）

**关键的一条**是玩家武器 DPS 与工人武器 DPS 的比值——它直接决定"早期玩家是主要生产力、后期被 SCV 取代"这条曲线。当前是 20 : 3.33（SCV 的 `FusionCutter` 是 5 伤害 / 1.5 秒），约 6 倍，落在基线要的"玩家远快于 SCV"里。

残骸从 2000 血 / 3 护甲降到 600 血 / 0 护甲，是为了让这个循环在一局里看得见：原来一个工人啃一堆残骸要 25 分钟。护甲归零也是刻意的——DPS 还在拍脑袋阶段，清理时间能直接从 DPS 心算出来比"数值更真实"重要。现在玩家一堆残骸 30 秒，工人 180 秒。

**注意维修是要花钱的**：原生 `Repair` 按目标造价扣物资。设备目前标价 125 矿，所以"修不修得起"本身就是个取舍——这是意外收获，但方向和设计一致，先留着。
