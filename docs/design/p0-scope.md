# P0 灰盒原型：范围与验证目标

## 唯一要验证的命题

> 玩家只有一双手，而**挖、打、修**三件事同时在抢他。

这是 `gameplay-baseline.md §9` 的核心张力，整个设计的地基。如果玩起来发现三件事其实不冲突——挖完就没事干，或者打架时根本不用管别的——那部门、协作、两层扇区全都建在沙子上。

P0 只做能验证这一条的最小集，其余一律推后。

| 清理产出 → 内层矿脉堆 | `25_clearing.galaxy` |
| 矿脉堆 → 物资（矿工**原生采集**，脚本只派工） | `40_economy.galaxy` |
| 设备供电（引擎 supply）、致命伤失能、可修复 | `20_devices.galaxy` |
| 工人自主派工（修优先于挖） | `30_workers.galaxy` |
| 扇区内层：主休息室核心、失守/夺回、休息室恢复 | `19_sector.galaxy` |
| 失能/恢复的通用机制（设备与核心共用） | `18_downable.galaxy` |
| 定时虫波（**待大修**，spawn point 结构会变） | `50_waves.galaxy` |
| 启动自检与灰盒读数 | `10_registry.galaxy` / `40_economy.galaxy` |

**失能是一个单位类型，不是状态位、也不是血量阈值。**致命伤把设备原地换成 `Lob_DeviceDown_Basic`：它不带 `Food` 所以立刻离开电网，带 `Invulnerable` 所以跳虫不再啃它而 `Repair` 仍然够得着。修满换回来。没有会和单位失同步的标志位，也没有"血量低于 X 就算停机"这种近似。

**清理建模为伤害而非自定义进度条**：残骸是高血量可破坏物，玩家和工人都靠攻击它来清理。这样血条直接充当进度反馈，而"玩家远快于工人"变成纯粹的武器数值问题，落在数据层可以随便调，而不是写死在脚本里的两个速率常数。

**矿脉堆是真的可采集节点。**之前是矿工站在原地、脚本把数字从变量搬进玩家账户——那是在宣称一件没有发生过的工作。现在 `Lob_Pile_Ore` 是个 mineral field（`RemoveWhenEmpty` 关掉，所以采空了也不会消失，还能被后续残骸续上），`Lob_Recycler_Basic` 是 drop-off，矿工走过去、装载、走回来，**引擎结算**。

脚本只剩派工。**产能的调参面是 `Lob_Pile_Ore` 的 `HarvestTime` 与 `HarvestAmount`**，直接设计这两个数（`IdealHarvesterCount` 只是 UI 上的建议显示，不影响实际收益），不要去算搬运距离——摆放是空间设计的事，产能是数值设计的事，把后者变成前者的函数只会让两边都动不了。

**核心是单位，休息室是 region，两者刻意分开。**

- `Lob_Core_Basic`（单位）回答"内层还守没守住"、归谁所有、以及之后部门与工事升级要挂的命令卡。基线 §3.2 本来就把"部门核心"列为内层内容。
- **主休息室是编辑器里画出来的 region**。休息室是个有墙的房间，绕着单位摆圆圈永远不是那个形状。而且它**不是固定的**——部门升级会改变作用范围，所以脚本实际测的是一个**运行时合成的 region**：初始是画出来那个的副本，之后可以被 `Sector_RestHallExtend()` 加进新形状。

绑定靠**包含关系**，不靠"名字里写玩家编号"的约定：谁的核心站在哪个 region 里，那个 region 就是谁的休息室。改玩家槽位或改名都不会让两边对不上。

失守可逆（§3.2），所以它用的是**和设备完全相同**的失能机制——核心变成 `Lob_CoreDown_Basic`，修好变回来。两者共用 `18_downable.galaxy`。

**玩家角色刻意不是工人**：`Lob_Hero_Agent` 没有采集、没有建造。抢它的只有要验证的那三件事，别的一概砍掉——这样"玩家很忙"就只剩一种解释。死亡只花时间：原地复活、不掉资源、角色不留惩罚，代价是走回来的路程加上这段时间里塌掉的东西（基线 §1）。

## P0 的结论怎么读

这一节比上面任何一节都重要。命题是可证伪的，就必须先写下"什么样算不成立"，否则玩完一局只会得到"感觉挺忙的"——而那不是结论。

**成立的样子：**

- 一局之内，至少 **3 次**明确感到"我现在必须放弃 A 去做 B"
- 三件事**都至少被放弃过一次**，而不是永远牺牲同一件
- 事后能说出"我当时要是选了另一边，会怎样"

**不成立的样子，以及各自意味着什么：**

| 观察到 | 说明 | 是设计问题吗 |
|---|---|---|
| 总有一件事**永远排在最后** | 三选一其实是二选一 | ✅ **是**，这是唯一的设计信号 |
| 三件事在时间上**不重叠** | 波次间隔太长，或残骸太少导致挖完就闲 | ❌ 场景规模 |
| 玩家**闲着** | 场景跑干了 | ❌ 场景规模 |
| 玩家很忙但**说不清在忙什么** | 抢手的东西超过三件 | ❌ 这正是作业标记 UI 被砍出 P0 的原因 |

**只有第一行是设计信号。**如果撞上的是后三行，改场景重测，不要动设计。

第一行还要继续往下分：

- **永远不修** → 设备损失的代价太轻。很可能是因为**电力还没有消耗端**，掉了不疼。那就说明这一条要等 P0.5 才测得了，而不是设计不成立。
- **永远不挖** → 清理的回报太慢或太远。
- **永远不打** → 虫波压力不够，或死亡代价太轻（死亡只花时间，如果那段时间里什么都不会塌，就等于不花）。

## 明确砍出 P0 的

**作业标记 + 队列 UI。**工人目前自动指派到最近的残骸。

理由：要验证的命题是"玩家自己的时间不够分配"，而玩家的取舍是关于**他本人在干什么**，不是关于微观调度工人。加一套下达指令的 UI 会给玩家增加第四件事，但对验证这条命题没有贡献，反而会让"手忙"的来源变得不可归因——测出来忙，分不清是设计成立还是 UI 笨重。

推到 P0.5。届时它需要一个英雄的目标性技能（数据层工作）。

同样推后的还有：防御工事、部门、理智、多人、多扇区。

**电力就是引擎的 supply 表，且没有任何脚本参与。**

设备带 `Food = 3`，引擎自己把存活设备算进 supplies-made，按玩家独立结算——正好是基线 §4.2 要的独立电网，白送。SCV 各吃 1 点（`Food = -1`，本来就有）。UI 常驻、超载自己变红。

**失能是一个单位类型，不是状态位。**设备挨到致命伤，就被 `Lob_DeviceDown_Basic` 原地替换：

- **不带 `Food`** → 出现的那一刻就离开电网。这就是失能机制的全部。
- **`Invulnerable`** → 一个标志同时办了两件事，而且两件都不用自己发明：跳虫武器的 target filter **排除** `Invulnerable`，所以没人会继续啃一台已经趴下的设备；而 `Repair` 的 filter **不排除**，所以 SCV 和玩家照样能修。
- 修满 → 换回在线型号。

**这砍掉了三样我发明出来的东西**：血量阈值（`c_deviceOnlineLifePercent`）、失能血量钳位（`c_deviceDisabledLife`）、以及整套 `SuppliesMade` 手写。基线 §4.5 的原话是"受到致命伤害时失能而非摧毁"——类型替换就是这句话本身，血量阈值是我自作主张加的近似。

上一版那个"引擎会不会覆盖我们写的 supply"的未知数，**随之整个消失了**：我们不再写它。

灰盒读数：

```
power=3/3 (1/1 devices online)
```

**电力还没有真正的消耗端**（照明、工事运行都不存在），所以 SCV 那 3 点负载是目前唯一的负载。

> 后续可以给失能→在线加一条 `CAbilMorph` 读条，让修复完成有个可见的收尾。现在是脚本直接替换，灰盒阶段够用。

## 数值起点

全是拍脑袋的占位，测的时候直接改：

- `Lob_Hero_Agent`：250 血、护甲 1、每秒回 1、移速 3.0
- `Lob_Hero_Rifle`：20 伤害 / 1.0 秒 / 射程 5 = 20 DPS
- `Lob_Debris_Normal` `LifeMax` = 600，`LifeArmor` = 0
- 每块残骸产出 120 点矿脉堆额度（`c_oreCreditPerDebris`）
- 矿工采集 5 点 / 2.786 秒（`Lob_Pile_Ore` 的 `CBehaviorResource`，数据层）
- 每个在线设备每 3 秒产 3 点电（`c_powerPerDevicePerTick`），血量低于 50% 停产
- 每 45 秒一波虫子，每个入口 `3 + 波次数` 只跳虫（`c_waveInterval` / `c_waveBaseSize`）

**关键的一条**是玩家武器 DPS 与工人武器 DPS 的比值——它直接决定"早期玩家是主要生产力、后期被 SCV 取代"这条曲线。当前是 20 : 3.33（SCV 的 `FusionCutter` 是 5 伤害 / 1.5 秒），约 6 倍，落在基线要的"玩家远快于 SCV"里。

残骸从 2000 血 / 3 护甲降到 600 血 / 0 护甲，是为了让这个循环在一局里看得见：原来一个工人啃一堆残骸要 25 分钟。护甲归零也是刻意的——DPS 还在拍脑袋阶段，清理时间能直接从 DPS 心算出来比"数值更真实"重要。现在玩家一堆残骸 30 秒，工人 180 秒。

## 场景规模检查（当前**不合格**）

数值对了不代表测得出东西。按现在图上摆的算一遍：

| | 现状 | 后果 |
|---|---|---|
| 残骸 | 2 块 | 玩家 30 秒一块，**第 60 秒就全清完了** |
| 矿脉堆总量 | 2 × 120 = 240 | 2 个矿工 5/秒，**48 秒抽干，然后经济永久归零** |
| 设备↔内层 | 3 格 | 跑过去修不要钱，"修 vs 打"这个取舍**不存在** |
| 虫群入口↔设备 | 12 格 | 虫子 3 秒就到，玩家没有决策窗口 |
| 首波 | 第 45 秒 | 到这时已经无事可做，之后只剩纯打架 |

**也就是说 P0 目前只在第 1 分钟内有信号，之后测的是另一个游戏。**

要撑住一局 10 分钟（13 波）的观察，场景至少需要：

- **残骸 14-18 块**。玩家全力清是 30 秒一块，工人 180 秒一块；玩家把一半时间花在清理上的话，10 分钟大约消耗 13 块。少于这个数就会提前跑干。
- **设备 ≥2 个，其中至少一个离内层 25-35 格**。角色移速 3.0，30 格单程 10 秒、往返 20 秒——对着 45 秒的波次周期才算真正的代价。设备贴脸摆，P0 白测。
- **虫群入口到设备要留出行军距离**，让玩家在"看到虫子"和"设备开始掉血"之间有得选。
- **矿脉堆和回收站放内层**。它俩现在被我扔在 (45,80) 和 (48.5,80)——猜的坐标，编辑器可能报放置冲突，直接拖走即可。摆哪里按空间设计来，产能调数据不调距离。

这些是编辑器侧的摆放工作，代码侧不用改任何东西——类型扫描是运行时的，摆多少认多少。
