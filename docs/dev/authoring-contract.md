# 编辑器侧 ↔ 代码侧 接口约定

编辑器侧负责**空间**（地形、房间、走廊、对象摆在哪），代码侧负责**行为**。这份文档是两者之间的唯一契约。

## 核心机制：按所属玩家分类

SC2 里编辑器摆放的对象在脚本中是靠数字 ID 引用的（`UnitFromId(7)`、`RegionFromId(3)`）。按 ID 对接意味着每摆一个对象就要把 ID 同步给代码侧——两台机器加一个 agent 共写一个仓库，这个账本迟早对不上。

所以改为**按所属玩家分类**：你在编辑器里摆单位，只要把它的 `Player` 字段设对，代码在初始化时扫描全图按玩家归类。

由此得到两条很值钱的性质：

- **代码里不出现任何编辑器 ID。** 你随便挪、随便删、随便加，代码不用动。
- **代码里不出现单位类型字符串。** 用什么单位当残骸、当设备完全随你，灰盒阶段想换就换。

## 玩家槽位表

| 槽位 | 用途 | 摆什么 | P0 需要 |
|------|------|--------|:------:|
| 1-6 | 人类玩家 | 玩家英雄起始单位 | 仅 1 |
| 7 | 虫群（Hostile） | 不预放，代码在运行时生成 | ✅ |
| 8 | **残骸** | 每个可清理的残骸堆放一个单位 | ✅ |
| 9 | **设备** | 每个周期产出装置放一个单位 | ✅ |
| 10 | **入口标记** | 纯标记，代码读完位置后会删除单位本身 | ✅ |
| 11+ | 预留 | 工事点位、核心、扇区锚点等，P0.5 再定 | — |

槽位常量定义在 `src/galaxy/10_registry.galaxy`，改动需两边同步。

## P0 灰盒摆放清单

一个扇区就够，先不做多扇区。

1. **地形**：一个内层房间 + 通向外层的走廊 + 外层一片开阔区。粗糙即可，不要花时间做美术。
2. **玩家 1**：内层放一个英雄单位（Marine 之类现成的顶替，P0 不做单位数据）。
3. **玩家 8 — 残骸**：外层走廊和开阔区里摆 8-12 个，堵住部分通路。用可破坏岩石或任意建筑都行。**关键是要摆出"清掉它才能过去 / 才能够到设备"的位置关系**，这是 P0 要验证的东西。
4. **玩家 9 — 设备**：外层摆 2 个，其中至少一个**被残骸挡住**，必须先清理才能用。
5. **玩家 10 — 入口标记**：外层边缘摆 1-2 个，虫群从这里进来。摆什么单位无所谓，代码读完位置就删掉它。

**摆放的设计意图**（不是随便摆）：内层核心、设备、虫群入口三者的距离关系，决定了"跑过去修" vs "留下来打"这个取舍存不存在。如果设备离核心太近，玩家不需要做选择，P0 就白测了。让至少一个设备远到跑一趟要付出真实代价。

## 编辑器侧需要的一次性设置

玩家 7-10 当前地图里还不存在（只有默认的 Neutral / Player 1 / Hostile），需要在 **Map → Player Properties** 里添加：

- 玩家 7：Control = Computer，作为敌对方
- 玩家 8/9/10：Control = Computer，Race = None，与所有人中立即可

它们是不是"真的"玩家不重要，只要单位能挂在这些槽位上、代码扫得到就行。

## 自检

地图加载后屏幕上会打印：

```
registry: debris=N devices=N spawns=N
```

数字对不上就是有对象的 `Player` 字段没设对。这比在编辑器里逐个点开看快得多。

> 如果三个数字全是 0，说明预放单位在 `InitMap()` 执行时还没创建完。届时把扫描挪到一个 0 秒定时触发器里即可，代码侧改一行。

## 区域（Region）暂不使用

区域没有"所属玩家"这个分类通道，只能靠 `RegionFromId`，会把 ID 账本问题带回来。P0 是单扇区，整张图就是扇区，不需要区域。

多扇区（P0.5+）时再解决，方向是用**锚点单位 + 半径**定义扇区，而不是编辑器区域——保持"代码不碰 ID"这条性质。
